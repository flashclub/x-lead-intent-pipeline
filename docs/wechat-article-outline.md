## 1. 开头钩子（300 字，场景化）

- 场景：每天有几千人在 X 上公开喊"求推荐"——"is there an app that…"、
  "anyone recommend…"、"I wish there was…"。这些是明牌的采购意向，
  但它们混在信息流里，没人接得住。
- 转折：我写了一个系统，实时抓这些帖子，并用一个**本地 CPU 模型**给每条
  打上 0-1 的购买意向分——单条推理 0.1 秒，模型文件只有 **199KB**。
- 配图位①：线上产品截图（搜索结果 + score 徽章 + 逐条耗时）
- 金句：「大模型负责判断力，小模型负责本能。」

## 2. 为什么不是"调 API 就完了"（400 字）

- 算一笔账：实时流场景下每条帖子调一次 LLM API 的成本与延迟
- 引出 System 1 / System 2 分工：**System 2（大模型）做老师，
  System 1（小模型）做本能**——正好呼应 TypeSafe AI 的 System One
  模型概念（外部验证：前 OpenAI 研究者创业公司 TypeSafe AI 押注同一方向）
- 本文立场：不训练大模型，**蒸馏大模型的判断力**

## 3. 全链路架构（300 字 + 架构图）

- 配图位②：管线架构图（采集 → 蒸馏标注 → 训练 → 部署四段）

## 4. 踩坑记（本章是全文核心，1200 字，三连坑）

### 坑一：teacher 标签倒挂（最贵的一课）
- 现象：第一版数据集 41 条"意向"里混着"recommend me some anime"
- 根因：teacher 提示词只看**表面句式**，不看**采购语义**
- 修复：正/反锚定示例写进提示词；人工抽查 50 条建立审计习惯
- 教训：**蒸馏的质量上限 = teacher 的质量上限**，先审计 teacher
- 配图位③：正/反例对照截图

### 坑二：49k 参数也会"训练不足"
- 现象：v1 模型全部分数挤在 0.25-0.40，判别力为零
- 根因：批量训练只走了 30 步梯度更新
- 修复：mini-batch + 早停 + 独立测试集
- 教训：**参数少 ≠ 好训练**；验证集指标要先怀疑再相信
- 配图位④：新旧模型分数分布对比图

### 坑三：U+2028 数据陷阱（工程师会心一笑）
- 现象：12 条帖子永远标不上，读取时"消失"
- 根因：X 帖子里的 U+2028 行分隔符 + `str.splitlines()` 会按它再切一刀
- 教训：**永远按 \n 迭代文件对象，不要用 splitlines() 读 JSONL**
- （一句话带过即可，技术读者会记住）

## 5. 效果：数字与实测（400 字）

- 数据：7,866 条标注（2,850 意向 / 5,016 噪音），三路切分，test 1,179 条
- 指标表：test precision@5 = 1.00 / accuracy = 0.877
- **诚实声明**（必须有）：这是"与 teacher 的一致率"（teacher 人工一致率 ~90%），
  不是 ground truth；方向安全——漏报不污染队列
- 实测对比表：采购意向帖 0.99 / 电影帖 0.02 / 求推荐博主 0.0002
