从零训练一个 49K 参数的文本分类器：PyTorch 小模型完全指南

不微调大模型、不调用 API、不需要 GPU——只用 PyTorch 和 7,866 条文本，训练一个能在 CPU 上 0.1 秒完成推断的二分类器

你要做什么

给 X（Twitter）帖子打一个 0-1 的购买意向分：判断发帖的人是在找东西买，还是在找东西消遣。

输入是一段文本（帖子内容），输出是一个 0 到 1 的分数——越接近 1，发帖人越可能在找产品买。

底座是一个冻结的嵌入模型（Google 的 embeddinggemma-2），它把任何文本压缩成 768 维向量。我们不训练这 740M 参数——它是 Google 用海量数据预训练好的"语义压缩器"，直接用。

我们只训练一个 49,281 个参数的 MLP 头：768 → 64 → 1。这个头的工作是在 768 维的语义空间里画一条分界线——线的一边是"要买东西的人"，另一边是"找东西消遣的人"。

前置知识

你只需要会 Python 和 PyTorch 基础（会写 nn.Linear 和 optimizer.step()）。不需要 GPU，不需要机器学习背景。

💡 本文所有代码来自一个真实上线运行的项目（X Lead Miner），不是教学 toy example。数据集、超参数、每一个坑都是实际踩过的。

第 1 步：数据准备

数据格式是 JSONL，每行一条帖子：

{"text": "is there an app that tracks competitor pricing daily?", "label": {"intent": true, "type": "recommend_request", "confidence": 1.0}}

共 7,866 条（2,850 条意向 / 5,016 条噪音）。标注来自 Gemini 2.5 Flash（teacher），提示词里写死了正反锚定示例：

✓ true: "anyone recommend a CRM for my agency"
✓ true: "wish an app tracked my subscriptions"
✗ false: "recommend me some anime"
✗ false: "recommend a good youtuber"

锚定示例是 teacher 质量的关键。没有它，Gemini 会把"求推荐动漫"也标为 true——因为两者都含 "recommend"，但商业含义完全不同。

⚠️ 第一版提示词没有锚定示例，导致 41 条"求推荐动漫/书籍"被标为 true。先审计 teacher，再训练模型。

数据清洗与去重

def load_dataset(path):
    rows, seen = [], set()
    for line in open(path, encoding="utf-8"):   # 只按 \n 迭代，不用 splitlines()
        if not line.strip():
            continue
        try:
            r = json.loads(line)
        except json.JSONDecodeError:
            continue                             # 容忍撕裂行
        rid = str(r.get("id") or f"row-{len(rows)}")  # 匿名数据合成 id
        if rid in seen:
            continue                             # 去重
        seen.add(rid)
        label = r.get("label")
        if isinstance(label, dict) and isinstance(label.get("intent"), bool) and len(r["text"]) >= 20:
            rows.append(r)
    texts = [r["text"] for r in rows]
    labels = [1 if r["label"]["intent"] else 0 for r in rows]
    return texts, labels
🪤 陷阱：X 帖子含有 U+2028（Unicode 行分隔符）。str.splitlines() 会按它切分字符串，导致 JSONL 行被撕成碎片、解析失败、静默跳过——你不会看到任何报错。永远按文件对象迭代（只按 \n 切）。

三路分层切分

def stratified_split(labels, frac=0.15, seed=7):
    """切成 train / val / test 三份。test 从不参与训练和早停。"""
    rng = random.Random(seed)
    by_class = {}
    for i, y in enumerate(labels):
        by_class.setdefault(y, []).append(i)
    val, test = set(), set()
    for indices in by_class.values():
        rng.shuffle(indices)
        n = max(1, int(len(indices) * frac))
        val.update(indices[:n])
        test.update(indices[n : n * 2])
    train = [i for i in range(len(labels)) if i not in val and i not in test]
    return train, sorted(val), sorted(test)
⚠️ 另一个陷阱：如果 JSONL 有重复 id（追加写入导致的），同一条帖子会同时出现在 train 和 test 里——模型只是"背住了"这条帖子。必须按 id 去重后再切分。

第 2 步：模型定义

import torch
from torch import nn

class IntentHead(nn.Module):
    def __init__(self, input_dim=768, hidden=64):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(input_dim, hidden),  # 768 → 64（49,152 + 64 参数）
            nn.ReLU(),
            nn.Dropout(0.2),               # 防过拟合（小数据集必须）
            nn.Linear(hidden, 1),          # 64 → 1（64 + 1 参数）
        )

    def forward(self, x):
        return self.net(x).squeeze(-1)     # (batch,) 而非 (batch, 1)

总参数：49,281。模型文件保存后 199KB（fp32）。

为什么 49k 参数就够了？因为底座已经把 7.4 亿参数的"理解语言"压缩成了 768 维的语义向量——你只需要在这 768 维的空间里画一条分界线。这条线的几何复杂度很低（近似线性），49k 参数绰绰有余。

第 3 步：嵌入编码

用冻结的嵌入模型把文本转成 768 维向量。这一步只需要跑一次（结果缓存到磁盘），后续训练和推理都用缓存。

from sentence_transformers import SentenceTransformer
import torch

embedder = SentenceTransformer(
    "google/embeddinggemma-2",       # 或 BAAI/bge-base-en-v1.5（更小更快）
    device="cpu",
    model_kwargs={"dtype": torch.float32},
)

# 关键：normalize_embeddings=True
# 这让所有向量变成单位向量（L2 范数 = 1），
# 使得余弦相似度等价于点积——对下游的线性层很重要。
features = torch.tensor(
    embedder.encode(texts, normalize_embeddings=True)
)
# shape: (n_texts, 768)
⏱ 编码是训练流程中最慢的一步（7,866 条 × fp32 CPU ≈ 10-30 分钟）。结果缓存后，后续训练只需几秒。

第 4 步：训练循环

这是整篇教程的核心。99% 的教程不会告诉你这一步——但恰恰是这一步决定了模型的生死。

反例：为什么 30 步全批量训练不够

最初版本的训练代码长这样：

for epoch in range(30):
    optimizer.zero_grad()
    loss = loss_fn(head(x_train).squeeze(-1), y_train)  # 全批量
    loss.backward()
    optimizer.step()

看起来完全合理——标准的 PyTorch 训练循环。但它有一个致命问题：全批量训练每轮只走 1 次梯度更新，30 轮 = 30 次。一个 49k 参数的模型从随机初始化到收敛，30 步远远不够。

实测结果：所有帖子的分数挤在 0.25-0.40 的窄带里，accuracy = 75.8%（恰好等于"全预测为负"的基线）——模型实际上什么都没学到。

🪤 教训：梯度更新次数 = epochs × (n_samples / batch_size)。全批量 30 epochs 只有 30 步。改成 batch=16 后，30 epochs 产生约 6,000 步——差了 200 倍。

正确的训练循环

torch.manual_seed(7)
head = IntentHead(768)
optimizer = torch.optim.Adam(head.parameters(), lr=1e-3)
loss_fn = nn.BCEWithLogitsLoss()

generator = torch.Generator().manual_seed(7)
best_val_loss = float("inf")
best_state = None
stale = 0

for epoch in range(200):  # 上限 200，早停会提前结束
    head.train()
    perm = torch.randperm(len(x_train), generator=generator)
    for start in range(0, len(perm), 16):  # batch=16
        idx = perm[start : start + 16]
        optimizer.zero_grad()
        loss = loss_fn(head(x_train[idx]).squeeze(-1), y_train[idx])
        loss.backward()
        optimizer.step()

    head.eval()
    with torch.no_grad():
        val_loss = float(loss_fn(head(x_val).squeeze(-1), y_val))

    if val_loss < best_val_loss - 1e-4:
        best_val_loss = val_loss
        best_state = {k: v.clone() for k, v in head.state_dict().items()}
        stale = 0
    else:
        stale += 1
        if stale >= 20:  # 20 轮没进步就停
            break

if best_state:
    head.load_state_dict(best_state)  # 恢复 val_loss 最低的那组权重

三个关键设计：

mini-batch：每轮 5,508/16 ≈ 345 步 × 数百轮 = 数万步梯度更新（修复前只有 30 步）。

早停 + 最优权重恢复：不是保存"最后一轮"的权重，而是保存"val_loss 最低"的那组。因为过了最优解后 train_loss 会继续降（过拟合），但 val_loss 开始升高——最后一轮不是最好的。

Dropout(0.2)：只在 train 模式生效，eval 时自动关闭。防止 49k 参数在 5k 样本上过拟合。

第 5 步：评估

不要只看 accuracy——在一个不平衡数据集上，accuracy 会被多数类绑架。需要看多个指标：

head.eval()
with torch.no_grad():
    val_scores = torch.sigmoid(head(x_val).squeeze(-1))
    test_scores = torch.sigmoid(head(x_test).squeeze(-1))

def precision_at_k(scores, labels, k):
    top = torch.argsort(scores, descending=True)[:k]
    return float(labels[top].float().mean())

for name, sc, lb in [
    ("val",  val_scores,  y_val),
    ("test", test_scores, y_test),
]:
    print(f"{name}: p@5={precision_at_k(sc, lb, 5):.2f} "
          f"p@10={precision_at_k(sc, lb, 10):.2f} "
          f"acc={((sc > 0.5) == lb.bool()).float().mean():.3f}")
📌 precision@k 比 accuracy 更重要：产品只展示排名靠前的帖子，你不在乎排名尾部的准确率，只在乎"排在前面的到底准不准"。

方式 B：Worker 内置权重（无 Python 进程，边缘推理）

把训练好的权重导出为 JSON，直接嵌入 Worker 代码——推理时不需要加载任何模型文件。

// 导出权重（Python 端执行一次）
import json
sd = head.state_dict()
json.dump({
    "w1": sd["0.weight"].tolist(),  # (64, 768)
    "b1": sd["0.bias"].tolist(),
    "w2": sd["3.weight"].tolist(),  # (1, 64)
    "b2": sd["3.bias"].tolist(),
}, open("intent-head-weights.json", "w"))
// Worker 端：纯 JS 矩阵运算，零依赖
const hidden = W.b1.map((b, j) => {
  let acc = b;
  const row = W.w1[j];
  for (let i = 0; i < emb.length; i++) acc += emb[i] * row[i];
  return Math.max(0, acc);  // ReLU
});
let logit = W.b2[0];
for (let j = 0; j < hidden.length; j++) logit += hidden[j] * W.w2[0][j];
const score = 1 / (1 + Math.exp(-logit));  // sigmoid

常见坑

坑症状根因修复
梯度更新次数不足全部分数挤在窄带，accuracy = 多数类基线全批量 × 少 epochs = 极少梯度步mini-batch + 更多 epochs + 早停
teacher 标签噪声模型学到表面模式（如"含 recommend = true"）teacher 提示词缺少排除条件显式正反锚定示例写入提示词
U+2028 数据丢失12 条帖子在所有代码路径中不可见str.splitlines() 按 Unicode 行分隔符切分文件对象迭代，不用 splitlines()
train/test 泄漏重复帖子同时出现在两边JSONL 追加写入产生重复 id按 id 去重后再切分
过拟合train_loss ≈ 0 但 val_loss 上升模型太大 / 数据太少 / 训练太久Dropout + 早停 + 最优权重恢复
